## 3. 外部 API 與即時資料契約

### 3.1 API 已知事實

- 企業提供固定的 `values`、`groups`、`configs` 三組 API（JSON）。
- 感測器資料大約每 **3 分鐘**更新；企業目前的可取得時段依使用者提供資訊為 **每日 09:00–17:00（台灣時間）**。
- API 受來源 **IP 白名單**限制；團隊在有授權對外 IP 的學校網路，或其他已被企業授權的網路，才可能成功連線。
- 正式展示方式：每位組員使用自己的 Windows/macOS 筆電，在本機執行 Dashboard／後端／資料庫，連接學校網路並開啟瀏覽器操作。**API 由本機後端/Collector 請求，不要把內部位址或憑證暴露給瀏覽器。**
- Docker Desktop 一般透過主機對外網路連線，不會自動改成不同的對外白名單來源；但學校 Proxy、VPN、TLS 或防火牆可能造成「主機可連、容器不可連」，仍需在授權網路實際測試。

### 3.2 範例 JSON 實際結構

這一輪範例可確認：

| 端點 | 結構與用途 | 範例結果 |
|---|---|---|
| `values` | `response.data[sensor_id]`，每筆有 `id`、`status`、`updateTime`、`values` | 48 個感測器；8 個 `lamp` 欄位有 blue/green/red/white/yellow；其他多為 `values.value` |
| `configs` | `response.data[sensor_id].config`：`displayname`、`type`、`unit` | 48 個感測器，含 lamp、analog、detector、string |
| `groups` | `response.data[]`：`groupId`、`groupAlias`、`sensors`、排序資訊 | 5 群：列印 A 區、列印 B 區、智能電錶、B4 列印狀況、B4 參數設定 |

Sensor ID 是三組資料的主要連接鍵。**不能只靠 Sensor ID 猜中文欄名或所屬區域。** 其中 `SRIP` 在本次 `values/configs` 存在，但未出現在 `groups` 的 47 筆群組指派內，不可假設每個感測器必有群組。A1–A4、B1–B4 的主要狀態及 A/B 區溫濕度是第一版範圍；智能電錶與 B4 特有進度/參數資料列為未來擴充。

注意：`values.values.value` 有時是**數字字串**，也可能是帶單位或特殊格式的字串；燈號則是多個顏色旗標。`values.status` 的數值也不能未經企業定義就直接等同「機台正常／故障」。感測器 `updateTime`、API `responseTime`、本機 `fetched_at` 與每輪 `batch_time` 是不同時間概念，不可混用。

### 3.3 參考 Python 程式與風險

- `test.py`：依序請求三個端點，保存含 `batch_time`、`fetched_at`、`endpoint`、`response` 的 JSON，按端點/日期分類。
- `scheduler.py`：以台灣時間每三分鐘整點後 **15 秒**執行 `test.py`；可參考排程設計，但**不是必須原樣移植**。
- 舊範例使用 `verify=False` 停用 HTTPS 憑證驗證，只能視為測試期間的臨時做法。**正式設計須維持 TLS 驗證，並確認企業憑證/信任鏈方案；不得默默關閉驗證。**

## 4. 歷史 Excel 格式與資料語意

### 4.1 固定匯入格式（已確認）

團隊會持續以相同清洗流程產生 **每日一份** 的標準化 Excel；工作表與欄位固定，資料日期及筆數變動。**v1 只接受此標準化格式，不接受原始公司 Excel 直接匯入，不重新做完整清洗。**

標準化範例共有六個工作表：

1. `machine_3min`：三分鐘燈號時數、換算值與品質註記。欄位：`日期`、`時間`、`區間開始`、`區間結束`、`機台`、`區域`、`None秒`、`Red秒`、`Yellow秒`、`Green秒`、`Blue秒`、`White秒`、`四態合計秒`、`加工小時`、`待機小時(黃燈)`、`異常小時`、`未開機小時`、`區間加工比例`、`開機加工比例`、`品質狀態`、`品質備註`。
2. `environment_3min`：`日期`、`時間`、`區間開始`、`區間結束`、`區域`、`感測器編號`、`類別`、`平均`、`最大`、`中位數`、`最小`、`參考門檻`、`最大值判斷`、`品質狀態`、`備註`。
3. `alarm_events`：`事件時間`、`感測器`、`感測器ID`、`類型`、`群組`、`規則名稱`、`規則條件`、`當前值`、`持續時間原文`、`初步事件分類`、`分類狀態`。
4. `quality_issues`：`日期`、`時間`、`對象`、`問題`、`區間合計秒`；可以只有標題列、無問題資料。
5. `data_dictionary`：`項目`、`定義/規則`、`說明`；清洗與運算意義的主要依據。
6. `README`：當日資料筆數、來源檔、品質與處理摘要；**這是 Excel 內的工作表，不同於新版程式根目錄 `README.md`**。

範例的 `README` 工作表列出 `machine_3min` **3,840 筆**、`environment_3min` **3,840 筆**、可取得 Alarm **11 筆**；這只代表 2025-06-01 範例，不是每一天都保證完整或都有 Alarm。範例資料字典版本標為 **「IT確認版 v3 / 2026-11-12」**，其中仍有標示「待企業確認」的細節，不得當成全部已獲企業最終背書。

### 4.2 清洗與分析不可破壞的規則（已確認）

- 每台機台三分鐘一區間、每日理論 480 區間；**缺少時間或缺日不補造紀錄**。
- `時間` 是**區間結束標籤**，例如 `10:39` = `10:36–10:39`。來源標籤 `24:00` 保留，完整區間結束時間為**次日 00:00**，但來源日期仍歸當日。
- 燈號六態：`None`、`Red`、`Yellow`、`Green`、`Blue`、`White`。`None` 依範本表示未開機，**不等於六態全部缺漏**。
- 同列六態有有效非負數值時，其他 **NaN** 可依已確認清洗規則補成 **0 秒**並標註；六態全 NaN 不補零。`Await`、空白、其他無法辨識的字串不可直接套部分 NaN 規則。**數值 0 是有效零，不是缺值**。環境 NaN/Await 保留缺漏，不能補成 0 度或 0%RH。
- 六態合計預期約 **180 秒 ±1 秒**，這個容差為暫定檢查值；不為湊 180 秒而修改既有有效值。負值、非數值、缺漏及超差應保留並標記。
- `Green` = 加工中；`Yellow` = 黃燈狀態，**不直接稱為待機**；`Red` = 紅燈狀態，**不能直接稱為已確認的實際故障**；`Blue/White` 原值保留，非零標記；`None` = 依範本未開機。
- `Green 秒 / 3600` = 加工小時；`Yellow 秒 / 3600` = 欄位 `待機小時(黃燈)` 的數字意義；`Red 秒 / 3600` = `異常小時` 欄位的數字意義（不等於已確認故障）；`None 秒 / 3600` = 未開機小時。
- `四態合計秒 = None + Red + Yellow + Green`；`區間加工比例 = Green / 四態合計秒`；`開機加工比例 = Green / (Red + Yellow + Green)`。**品質通過且分母 > 0 才能計算比例**，缺漏或分母 0 留空，不稱正式 OEE／稼動率／設備績效。
- 圖表的**六態時間占比**若需呈現六種狀態，應以可用且有效的六態秒數合計作分母，**不能直接拿四態加工比例充當六態占比**；跨多筆資料應先累加有效秒數再算比例，不平均各筆百分比。資料品質排除範圍及分母細節於完整設計階段再明訂。
- **相鄰有效三分鐘區間「純綠 → 純黃」**可標為「列印完成」的區間邊界判讀；同區間綠黃都有秒數且順序未知時僅為「疑似完成」。不能跨缺漏推斷切換，不能宣稱精確秒級時間，也不能轉換成完工件數、產量或良率。
- 環境 AVG/MAX/MED/MIN 保留既有值；26°C / 40%RH 只是**待企業確認的參考門檻，不是正式合格規格**。
- Alarm 的事件時間不強制對齊三分鐘；保留原始觸發規則、感測器、當前值、持續時間原文與分類註記。缺少 Alarm 來源≠確定零警報；「列印完成」警報也不等於故障。
- 保留匯入檔中的**品質狀態、備註、來源與警報來源狀態**。`quality_issues` 雖不做獨立「資料品質頁」，仍是匯入與正確分析的重要資料。
- **新系統的責任是驗證與匯入標準化檔，不是擅自重新清洗／改寫其既有原始數值**。有不一致時呈現錯誤並依規則決定阻止、排除或待確認，不可偷偷修復。

### 4.3 待完整規格補齊的技術細節

已掌握實際工作表及欄位，但 **SQLite 的最終 Schema 還沒有定稿**：仍須為每個欄位決定型別與 NULL、唯一鍵、索引、跨日時間表示、品質註記保存、資料批次版本及替換交易。此項是「映射與資料庫設計待完成」，**不是缺少 Excel 或需要 Codex 再猜欄位**。

建議的初步邏輯表（表名可調整）：`machines`、`history_machine_intervals`、`history_environment_intervals`、`history_alarm_events`、`history_quality_issues`、`live_sensor_readings`、`api_poll_runs`、`import_batches`。可增加必要的 metadata；**同一 SQLite 資料庫、即時與歷史不同資料表和資料生命週期**，不必預設建兩個獨立 DB。這只是設計方向，Stage 1 先評估，不要建立 migration。

### 5.2 機台監控（即時）

- 頂部可保留整體設備總覽，但數字必須由真實且新鮮的資料決定。
- 區分 Green、Yellow、Red、None、其他、未知與資料過期／未連線；**不要將五個顏色旗標全 0 直接推定為正常或離線，也不能將 API `status` 數字自行映射成故障原因**。
- 智慧電錶、B4 專有進度/參數第一版**不做**，列未來擴充。未定義欄位不可顯示假資料。

### 5.3 環境監測（即時）

- 保留 A/B 區溫度、濕度目前值卡片。
- 下方用時間序列折線圖顯示溫度與濕度；來源是 **Collector 自行累積的即時 API 快照**，因為單次 `values` 不是歷史序列。
- X 軸固定展示**當日 09:00–17:00（台灣時間）**；未收集的時間保持空白，不補 0、不任意插值；收集途中斷線要留空段。
- 兩區各有**兩組溫度、兩組濕度**量測，應可區分感測點，不能未說明就自行取平均。建議提供溫度／濕度與 A／B 區篩選（互動細節可在 Stage 2 確定）。
- 顯示最後資料時間與是否過期；不能把過期值當前值無提示地展示。

### 5.4 歷史加工分析（從標準化 Excel／歷史 DB）

大圖卡右上有 **「區間分析／同期比較」** 切換；兩種模式共享同一套歷史計算與圖表元件。

**區間分析**：開始日期、結束日期、資料粒度、機台篩選。原需求：「小於一天選 30 分鐘或 1 小時；大於一天選 1 天」；建議把同日視為細粒度模式、跨日改以天呈現，但**如涉及新增時分選擇器，先確認 UX，不要擅自改產品需求**。

**同期比較**：可選「日對日／週對週／月對月」。日對日選兩個日期；週對週各選一個起始日，形成連續七天；月對月分別選年與月。不同天數或缺日要清楚顯示資料涵蓋程度，不能讓無資料被當成零生產。

兩模式共用三張圖：

| 圖 | 區間分析 | 同期比較 |
|---|---|---|
| 累積加工工時排行 | 橫向長條；Y 軸機台、X 軸 Green 小時 | 同機台兩期間並列長條 |
| 加工時間趨勢 | 時間序列；各桶加總 Green 秒再換算小時 | 將兩個期間按相對時間桶對齊比較，標示原始日期 |
| 燈號時間占比 | 六態各占有效狀態時間比例（例如 100% 堆疊長條） | 兩期間比較六態組成；缺值/品質規則需一致 |

**「歷史加工分析」不是正式 OEE 稼動率分析**；主指標 Green 加工時數，不能無依據稱為產能、產量或故障率。

### 5.5 異常事件分析（歷史）

使用既有 `alarm_events` 及 `machine_3min` 分析：

1. **機台紅燈**：累積紅燈時數、機台及時段分布；不宣稱實際故障根因。
2. **機台黃燈**：累積黃燈時數、分布；不直接寫成「待機」或「故障」。
3. **環境 Alarm**：顯示標準化 Excel 已提供的環境警示、觸發規則、感測器、當前值、事件時間及持續時間原文。
4. **事件明細**：可依日期、區域、機台／感測器、類型篩選；應標明來源與資料性質。

注意：連續數筆紅燈三分鐘區間不等於等量「故障事件數」；如要合併成連續狀態區間，需有明確、不跨缺漏的規則。不要自行發明 AI 故障診斷或未被支持的事件次數。

### 5.6 Excel 匯入（歷史資料管理）

- 支援一次選多個**標準化** Excel；選取後先顯示檔案清單，可移除錯誤選取的檔案。
- **預覽 → 驗證 → 顯示新增/重複/衝突/錯誤摘要 → 使用者最終確認 → 寫入資料庫**。不能一選檔就直接持久化。
- 驗證工作表與必要欄位、資料型別、日期一致性、區間時間、基本數值和必要品質欄位；可合法為空的工作表（如 `quality_issues`）不得因此判失敗。
- 相同資料重複上傳應略過；同日不同內容視為修正檔衝突，讓使用者明確選擇保留或替換。**替換時必須交易式完成**，不可發生部分日資料被覆蓋、另一部分未更新。
- 要保存匯入批次、來源資訊、匯入結果與錯誤摘要，供後續檢查。
- 第一版**不需要**支援原始網站 Excel → 標準化 Excel 的自動清洗轉換。

### 5.7 API 連線設定（以觀測與診斷為主）

- 三組 API 位置固定，不再提供使用者任意修改 API URL 的輸入表單。
- 顯示模式（Live/Demo）、每個端點連線狀態、最近成功時間、最近取得資料時間、是否過期與可理解的錯誤原因。
- 提供**手動測試連線**，由後端執行；不得在 Demo Mode 偽裝成功連上企業 API。考慮 09:00–17:00、白名單和 TLS 失敗的區別。
- API 連線失敗時**不自動切換 Demo Mode**；使用者手動切換才進入 Demo，畫面顯著標示「模擬／測試資料」。

## 6. 部署與技術架構（目前是初步建議）

初步偏好：

| 層次 | 初步方向 | 定案條件 |
|---|---|---|
| 前端 | Next.js + React + TypeScript | 檢視舊 UI 與套件後確認版本與元件移植方案 |
| 後端 | Next.js Route Handlers，暫不另建 Python API 服務 | 評估匯入/查詢/排程能否保持簡單 |
| 資料庫 | SQLite（同 DB，不同歷史及即時資料表） | 資料型別、索引、交易、備份與寫入競爭設計確認 |
| 排程收集 | 後端以外的明確 Collector／Worker 執行個別三分鐘排程 | 不依賴網頁開啟，確認容器執行與關閉策略 |
| 部署 | Docker Compose（本機） | Mac/Windows 實測；資料庫持久化 volume；Network/TLS 測試 |
| 套件管理 | npm（沿用現有習慣） | 若舊版使用不同 lockfile，再評估 |
| Git | `jiyin-dashboard-v2` 內獨立 repo | 禁止把公司資料、API Key、`.env`、資料庫或大型快照提交公開 Git |

使用者曾考慮若改 Python 則採 `uv`，但**目前無需因 Excel 匯入就增加 Python 服務**。若 Codex 證明 Python 能實質降低複雜度，可提出替代方案及代價，**不要直接切換技術棧**。

即時與歷史邏輯區分：

```text
企業 values/groups/configs API ──> Collector ──> 即時快照資料表（短期） ─┐
                                                                     ├─> 後端查詢／統計 ─> Dashboard
標準化每日 Excel ──> 預覽／驗證／匯入 ──> 歷史資料表（長期） ────────────┘
```

- 即時資料短期留存原則上可**先考慮 3 天**，只是合理候選、尚未最終定案；須能正確清除舊快照而不影響歷史資料。
- 每位組員在自己筆電啟動，SQLite 預設**各自獨立，不做跨筆電資料同步**。
- Docker image/容器重建不能讓 SQLite 遺失；資料庫需要持久化 volume 與可還原備份方式。
- 時間統一明確使用 `Asia/Taipei` 語意；避免把 UTC API 時間與歷史區間結束標籤混淆。

### 6.1 Live / Demo Mode（已確認）

- **Live Mode**：真正請求企業 API；若無法連線，忠實顯示失敗、過期或無資料，不用模擬資料偷偷代替。
- **Demo Mode**：在外部網路、非 API 開放時段及離線展示時使用。可取 `test_api/` 已收集的多次快照或明確標記的測試 fixture；需能形成合理的 UI 測試狀態，但不把測試資料寫進正式歷史表或冒充 Live。
- 兩模式由使用者**明確手動切換**；歷史分析僅使用 Excel 匯入的歷史資料，與 Live/Demo 狀態分開。
- 與 API 相關的 URL、Token、憑證須從受保護的環境設定載入；不得直接在前端 bundle、GitHub 或 log 中洩漏。

## 7. 驗收與測試重點

先確定資料契約和測試條件，再逐階段實作。測試應與風險成正比，不必每寫完一個小 UI 元件就額外派 Sub-agent。

- **歷史匯入**：有效範例可匯入；完全相同重複匯入不增筆數；同日修正版須人為確認、可回滾；錯誤欄位/缺必要工作表/非法日期阻止錯誤入庫；允許 `quality_issues` 無資料。
- **時間與品質**：正確處理 24:00、跨日、None vs 缺漏、部分 NaN 補零語意、Green 小時加總、比例分母 0、欠缺資料不補造。
- **圖表**：排行榜、趨勢和時間占比數字能以小型已知案例驗證；日/週/月比較正確處理桶對齊與不同資料涵蓋範圍。
- **API**：JSON 欄位映射、超時、個別端點失敗、過期資料、非白名單、離線、Demo Mode 標示；同輪定期取得無重複與未核准外部請求。
- **UI**：七個頁面可以操作、篩選及顯示空狀態；無資料不是顯示假數字；Live 失敗不自動 Demo。
- **部署交付**：在 Mac 和 Windows 至少演練所需指令；啟動後能開啟 `http://localhost:3000`；停止/重建容器後資料不遺失。
