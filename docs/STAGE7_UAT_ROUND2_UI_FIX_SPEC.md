## B. 修改項目（按優先順序）

### P1 — API 設定頁：手動測試結果與服務狀態一致

問題：當使用者按「測試連線」，總覽顯示「無法連線／最近測試時間」，但下方三端點仍寫「尚未檢查」，使用者無法判斷哪個端點有實際請求。資料層原本將 MANUAL_TEST 與 Collector 分開是**正確設計，不得取消**。

1. 先檢查 Stage 6 已有 `manual test` audit／endpoint audit 與 `/api/connection-status` 回傳；**優先沿用既有欄位與紀錄**，不得為畫面同步而將手動測試記錄寫成 Collector 成功或 readings。
2. 「資料服務狀態」四欄維持：**資料來源、目前狀態、最近檢查、訊息**；資料來源仍為設備數值（values）、設備設定（configs）、區域群組（groups）。顯示該端點**最近一次實際檢查**（可註明「手動測試」或「自動收集」來源，若來源能可靠取得）。
3. 若手動測試僅對 values 發出請求且逾時：values = 「連線逾時／無法連線」，最近檢查為**實際請求時間**，訊息為「未取得伺服器 HTTP 回應；可能是網路／白名單／服務不可用」；configs/groups **未被請求，仍為「未測試」**，可顯示「本次因前一端點失敗而未繼續」；不得把三項全部標失敗，也不得假裝白名單拒絕已證實。
4. 若測試成功或其他錯誤：按真正的端點結果分類「成功、HTTP 錯誤、API 回應錯誤、格式不符、TLS 錯誤、逾時、未測試」，使用簡短中文；不公開內部 IP、Origin、Token、憑證、堆疊追蹤。
5. 手動測試按下後立刻顯示 **正在測試…**、停用重複點擊；結果回來（含逾時）立即更新上方摘要與下方三端點列表，不必重新整理網頁。已設定 Timeout 20 秒，先**保留目前後端上限**，不要隨意改 Collector 的 timeout；若 UI 的 pending 狀態未正確復原，做最小修正。
6. 「未檢查」僅適用於真正沒有檢查紀錄的情況，不應為消除它而**在 `npm run dev`、開啟網頁、切換 Live 時自動送企業 API 請求**。Collector 的正式自動啟動留在 Stage 8 的統一系統啟動流程。
7. 如現有查詢介面無法從既有稽核紀錄安全取得上述顯示所需欄位，先做**最小範圍、可回歸測試**的查詢／UI 修正；不得重寫 Enterprise Client、Collector、修改資料庫 schema 或生成假的端點結果。

驗收 Mock 情境至少包含：未測試；values 網路逾時，configs/groups 未嘗試；三端點全部成功；單端點 HTTP/API/schema 錯誤；測試後 UI 即時刷新；手動測試不改變 Collector 和 Live readings。

### P2 — 機台監控：縮短卡片高度但維持左右等高

1. 現有四張機台卡頂端 ID／燈號與底部最後回報之間空白過大。**不是要求加入假 KPI，也不是加長欄位。**
2. 將 **A/B 區左邊四卡與右側詳情的「整區高度一起縮短」**；2×2 四卡可維持等高並均勻填滿左側，左側與右側底邊仍須對齊（桌面目標差值 0px，允許正常 subpixel rounding）。不要再透過撐高左側四卡來對齊過長的右側。
3. 右側詳情保持目前已簡化的內容；自然緊湊排版、減少不必要的上下留白與過大 padding，避免另加無意義資料。
4. A1 被選取時的白色內框／選取圈稍微**降低視覺權重**（更細或降低 opacity），但仍要能清楚區分選取和燈號。保留已經改善的五色高對比外框、柔和 glow、燈點。STALE/UNKNOWN/NO_DATA 保持中性。
5. 保留 A/B 獨立選取、詳情完成訊號與區域跳轉；窄版適度堆疊，不強制等高，不發生水平 overflow。
6. 若現有 API 沒有可靠「本次運轉開始時間／運行多久」，**不要為填空而推算**；可維持 ID、名稱、狀態、最後回報即可。

### P2 — 溫／濕度圖：畫線與警示線更易讀

1. 圖上現有水平小段的「階梯感」可能源自 **Demo 數值以 0.1 為單位重複**；先確認是不是直線連接；只允許視覺層修改線寬、線端及接點（`stroke-linejoin`／`stroke-linecap` 等）。**不得更改讀值、補插值、移動平均、使用會偏離實際讀值的平滑曲線**。
2. 四條觀測序列保持實線、**連續線段兩點以上無常駐圓點**、Hover nearest sample_slot 顯示逐筆值，鍵盤可操作；0 點空狀態、1 點顯示點；若多筆資料中有被缺口隔開的**孤立單點區段**，仍要以單點可見，不得因此消失；跨 NULL／不連續 slot 斷線，絕不接過缺口。
3. 26°C／40%RH 是企業提供的**正式儀表板環境警示值**；警示線改為對比足夠的**紅色系虛線**，略加粗；和目前粉色 B 區序列仍能以 dash pattern 區別。
4. 警示標籤只顯示 **`26°C`／`40%RH`**，貼近繪圖區右邊界的**專屬留白**，不能離得太遠或壓住資料線；在 1280/1366/1440 與窄版皆不裁切，Y 軸動態尺度不因標籤改動而失真。
5. 本輪先不加入全圖紅綠背景、淡紅遮罩或新的圖表模式；優先處理上面可讀性問題。
6. 保留 Stage 7 已確定的 Provider clock X 軸 09:00～17:00 漸進延伸、Y 軸穩定自適應、圖例 hide/focus 及刷新保留狀態。

### P3 — 監控頁的「重新讀取本機資料」

1. 機台監控與環境監測頁保留每 30 秒本機資料自動刷新；**不代表每 30 秒向企業請求**。
2. 將兩頁頂部過大的「重新讀取本機資料」按鈕改為低權重小型刷新 icon／操作，名稱 **「更新畫面」**（可用 tooltip 說明「重新讀取已儲存資料，不會向企業 API 發送請求」）。同時可在旁保留簡短「每 30 秒自動更新」。不要把它改叫「取得最新 API 資料」。
3. API 設定頁的「測試連線」保持獨立：會實際向企業固定端點請求（**本輪測試只能使用 mock**），但不寫 readings；這三種操作不能混淆。
4. 不改原有自動刷新、Live/Demo 時鐘及資料隔離邏輯。

## C. 非本輪範圍與安全邊界

- 企業 IP 尚未加入白名單；**本輪不發出任何真實企業 GET**，包括手動測試或自動啟動，所有連線情境只用 Mock API 測試。
- 不啟動真實 Collector、不改三分鐘收集時間、Sensor mapping、Live/Demo Provider、retention 或 SQLite schema。對資料服務查詢只允許必要且最小的兼容修正。
- 不修改正式 SQLite、Docker Volume、Stage 5 歷史 Excel／異常分析核心；不得 Push／部署／開始 Stage 8。
- 不要在 `npm run dev` 或頁面進入時偷偷啟動 Collector、直接發企業 API；未來統一啟動 Web+Collector 是 Stage 8 的工作。
- 不向 Git 提交 `_reference_inputs`、`.env.local`、企業 JSON／Origin／憑證、測試 DB 或截圖證據。

## D. 驗收與交付（避免過度測試）

- 先針對 4 類變更做相應單元／元件／API 測試（特別是手動測試稽核與三端點顯示）；再做 typecheck、lint、production build，必要時整套回歸一次。
- 用**合成／mock＋隔離 SQLite** 進行真實瀏覽器 smoke；至少 1366px 視覺對比與 1280/1440 桌面、760 窄版 overflow 檢查。
- API 設定：模擬 values 20 秒 timeout → 上方與下方 values 同步為失敗；configs/groups 未測試；下一次 mock 成功可以更新顯示，且不產生 Live readings。
- 機台：A/B 四卡與詳情依然等高，且相對 Round 1 **實際縮短高度**；已選取仍可辨且燈號外框更優先。
- 圖表：無常駐 marker、Tooltip 可取逐筆數值、警示紅色虛線與右側緊鄰標籤、不影響 null gap 和動態 X/Y。
- 不要為純 CSS 微調建立大量測試場景／超長文件。更新精簡 UAT acceptance 與 BUILD_LOG，建立**本機 Commit**、停止並回報截圖、已完成項目、尚未驗收的企業連線與 Commit Hash。
