## B. 不可違反的資料與安全契約

1. **歷史 Excel、Live API、Demo 完全分流**。Demo 是合成 read-only fixture，不寫 Live／History SQLite；Live 失敗不能自動切 Demo。不可動正式 DB、Docker Volume、資料收集與歷史分析邏輯。
2. Live 燈號與 freshness、connection/provider 是不同維度。五燈全零＝UNKNOWN，多燈同亮＝OTHER；過期／缺值不能顯示亮色「正常」。只對 fresh 且唯一有效的真實燈號強調對應色彩，selected 另有獨立效果。
3. **企業已明確提供警示數值**：溫度 **26°C**、濕度 **40%RH**。因此移除「暫定」「待確認」「並非企業正式警報門檻」等舊文案，使用「警示值」「警示門檻」「超過警示值」；**大於**門檻才為超標（等於門檻不超標）。這是本次更新的產品要求，應更新相關 UI 說明／規格附註。**仍須區分畫面即時閾值提醒與企業 API 回傳的原始 Alarm 事件**：不可因此新造 Alarm event、故障原因、品質不合格事件或新增未授權通知／資料表。
4. Sensor `updateTime`＝感測器／來源端資料更新時間；`fetched_at`＝本平台取得 API 回應時間；不是「請求發送時間」。不可把這兩個時間混成同一欄或冒稱請求開始時間。
5. 不將瞬間 lamp 訊號解釋為持續運轉時長，也不推算產量。只展示資料能可靠證明的事實。任何狀態起始時間／持續時間需有相鄰、完整、有效且可覆蓋真實開始點的變化紀錄才有解釋力，否則應顯示「無法判定」，**本輪先不新增此功能**，僅在結案中說明可行性。
6. 本輪使用 Demo 與隔離 DB；**禁止真實企業 API 呼叫、真實 Collector 長時間輪詢、Push、部署、刪除／重置 DB、修改 Excel 匯入／歷史統計核心**。不因 UI 改動去改 Stage 6 的數據模型。手動 API 測試仍只允許使用者主動操作並確認；本輪自動化不得點擊它。

## C. 機台監控頁｜視覺與內容精修（圖一／二）

### C1. 四卡與詳情 **同高，左側不能留白（新增高優先決策）**

- 每區桌面版維持「左：2×2 四張機台卡／右：該區獨立詳情」；A、B 區選取互不影響，移除 3D 場景的決策不變。
- **每一區左側整個 2×2 grid 的底部必須與右側詳情面板底部對齊；四張卡片均等高、均分左側可用高度。** 在右側內容較高時左側跟著撐滿；不要留下目前圖二那塊大面積下方空白。
- 優先 CSS Grid/Flex `stretch`、`minmax(0,1fr)`、子卡 `height:100%`／`flex` 的自然排版；不要用大量固定 `px`、絕對定位、假資訊或空白填充硬撐。卡內內容可垂直合理分布（上方標題與狀態，中間機台名，底部來源時間／可見異常）；保持可讀及不卡文字。
- 左右寬比可採約 55～60%：45～40%，依實際內容決定；主要驗收是**同高、無大片死白、卡片不擁擠**，不是拘泥某個比例。
- 窄版改成合理堆疊，解除桌面版強制等高；無水平頁面溢位。

### C2. 燈色辨識力

- 加強五色邊框的飽和度、描邊及少量外發光（glow）；與右上角 lamp badge 同色。綠／黃／紅／藍／白都能在深酒紅背景清楚區分。白燈在暗背景不過曝。
- `STALE`、`UNKNOWN`、`NO_DATA` 皆為中性外觀，不用先前燈色繼續發亮。`OTHER` 多色同亮不私自指定一個主色。
- 選取態用與燈色不同的明確 focus／選中輪廓；維持鍵盤與對比可用。裝飾簡潔不做霓虹過度閃爍。
- 可加一個小設備 icon、更新時間 clock icon、少量分隔／hover，**不新增無來源業務 KPI**。

### C3. 卡片與詳情的文案／欄位減法

- 機台卡：機台 ID、機台名稱、鮮明的燈號狀態、簡短最後回報時間。**移除反覆顯示「資料新鮮」**；正常時不必重複「正常」，只有來源過期／缺漏時用「資料已逾時」「尚無資料」「燈號無法判讀」等短提示。
- 右側詳情保留：機台代號與名稱、當前狀態（**不另外重複一列 `有效燈號 GREEN`**）、有意義的時間資訊、**「加工完成訊號」ON/OFF/無資料**（來源 detector；只顯示原始開關狀態，**不宣稱已完成加工或產量**）。
- 時間欄位用 **「來源更新時間」**（sensor.updateTime）和 **「平台取得時間」**（fetched_at）；若兩者一致可緊湊呈現，但不可改變語意。若來源沒有值顯示「無資料」，不可虛構。
- 將 `原始狀態`、`解析狀態 VALID`、`rawStatusMeaning=UNCONFIRMED`、`Detector 原始值` 等工程細節從一般詳情移除。**但保留完成訊號的使用者可讀 ON/OFF**，不能把已決定的 Detector 需求整個刪除；必要的 raw 值仍留在現有後端與測試，不因 UI 隱藏而丟失。
- 現有右側「A/B 區共用環境摘要」完整四個溫濕度卡片移除，避免與環境監測頁重複。若區域標題附近確有環境超標，可留一句精簡區域提示（例如「2 個測點超過警示值」）與頁面入口，但不要重畫四值。
- 若精簡後右側過矮，可用更好的資訊層次與合理間距，而非重塞工程欄位。**左右兩側仍需自然同高**。

### C4. 非本輪必做的「運行中多久」

- 本輪**不要**憑一個現在的綠燈推論「開始於 XX:XX／已運行 N 分鐘」。只有連續且可信的狀態轉換資料才可能建立受限的「可觀測狀態持續時間」，不等於機台真實加工開始時間。
- 如檢查現有資料發現有其他**已證實且使用者有用**的欄位，可於報告提出候選與依據；**未明確授權的新 KPI 不加到 UI**。

## D. 環境監測頁｜區域與感測卡精修（圖三）

- 保留 A／B 兩區並排、每區兩溫兩濕共八個測點、各自顯示不平均。
- 刪除區域抬頭下重複的「兩個溫度、兩個濕度測點各自顯示，不取平均」；如仍需提示，縮成區塊底部的小字 `* 各測點分開顯示，未做平均。`，可完全不顯示。
- 子卡改名 **「溫度監測器 1／2」「濕度監測器 1／2」**（優先採用 configs 穩定可對應的來源顯示名，若只為「列印A區溫度1」則可用上述簡短 UX 名稱），確保 A/B 區仍能辨認。
- 子卡右上角統一顯示**對警示門檻的狀態**：Fresh 且 numeric 合法、`value <= threshold`→「正常」；`value > threshold`→「超過警示值」；STALE→「資料逾時」；缺讀值→「尚無資料」；無法解析→「無法判讀」。後三者不能顯示綠色正常，也不能把 0 當缺資料。
- **邊框同狀態上色**：正常柔和綠、超過警示值明確紅、逾時中性橘灰、缺值中性灰。色彩與文字雙重傳達，視覺與機台狀態卡協調但不要讓正常環境卡過度發光。
- 子卡只顯示：名稱、狀態、適量溫度／濕度 icon、放大的數字與單位。卡片抬頭與狀態 badge 頂端對齊，標題不被 pill 擠壞。
- **移除每個子卡重複的來源更新／平台取得時間**。時間資訊移至各 A/B 區塊標題右側：例如「區域最近來源更新」「平台最近取得」；這是**四個感測點之中最新的時間，不保證每個測點都同時更新**。若有多個來源時間差異或個別異常，保留在 hover/focus 的細節讀取或另個輕量資訊入口，不得假裝整區所有 Sensor 同時刷新。窄版可以讓時間換行。

## E. 溫／濕趨勢圖精修（圖四／五；底色參考圖 00）

- 一張溫度四線圖，一張濕度四線圖；每張只留 **一次**「溫度趨勢」「濕度趨勢」主標題，清楚標示 Provider 時間範圍（Demo 用 manifest date/clock；Live 用台灣當日）。保留圖例 focus/hide、共用 Tooltip 和鍵盤。
- 移除標題下「四條獨立實線／缺漏時間格中斷」等工程說明；有必要時放卡片右下角小字 `* 每 3 分鐘記錄一次；缺漏資料不連線。`。不在圖內塞長段文字。
- 四條趨勢預設畫 **實線**。0 筆有效資料顯示尚無資料；1 筆有效資料顯示單一圓點；2 筆以上連續有效資料只畫乾淨實線，**不顯示每個三分鐘資料點的常駐 Marker**，也不能只把大圓點縮小。滑鼠在繪圖區移動時應吸附最近的有效時間格，不需要精確點中細線；Tooltip 顯示該時間格的數值、時間與來源，並只在 hover 時暫時突出資料點。鍵盤 Focus 仍可逐筆查看。圖例 hide/focus 與刷新後保留互動狀態維持不變。NULL、無觀測與不連續 `sample_slot` 依 Stage 6 規則保留斷線，不插值、不跨 gap 連線。
- 企業提供警示線：溫度 **26°C**、濕度 **40%RH**；**虛線**，顏色／線寬和趨勢足夠區分、顯示層級不被圓點蓋住。標籤只寫 `26°C`、`40%RH`，置於右端**專用圖外標籤留白區**或其他不覆蓋折線的固定位置，必要時調整 plot right margin，勿放在可能有資料線經過的圖內區域。
- 先以**清爽可讀**為優先；可選擇在警示線**上方**增加非常淡的紅色背景帶，若與四線競爭則不加。**不要做大面積紅綠雙色背景**。基準線對應的 Y 值必須始終在可視範圍內。
- X 軸依 Stage 7 已實作的 Provider 時鐘由 09:00 起逐步向 30 分鐘刻度擴展至 17:00；Y 軸動態 nice scale，但避免刷新時劇烈跳動。不要改 `sample_slot`、Demo 時間或 Collector 排程。

## F. API 連線設定頁精簡（圖六／七／八）

### F1. 頁面結構

- 移除持久顯示的「已切換為 DEMO／LIVE 模式」**成功通知長條**；模式卡已顯示目前狀態。**操作失敗時仍須顯示錯誤提示**，不可為了乾淨隱藏失敗。
- 用一般使用者可讀文案取代 `Collector`、`MANUAL_TEST`、`Schema`、`responseCode` 等詞。頁面呈現一個整合的資訊流，不是開發者監控台。
- 推薦四個區塊（可合併成更精簡視覺）：
  1. **資料模式**：Live / Demo，及一句清楚差異（Demo 為模擬資料，不代表企業 API 已連線）。
  2. **自動資料收集**：目前收集狀態、最近成功取得資料的時間；若無資料就寫「尚未取得」。
  3. **手動連線測試**：按鈕、上次測試時間／結果、非服務時段提醒；保留真實 API 請求確認與服務端限制，不在本輪觸發。
  4. **三項資料服務狀態**：精簡端點表。
- 不再用兩張同等分量的大卡重複顯示「最近結果／最近嘗試／最近成功／最新資料」。能幫使用者行動的最重要資訊置前，次要資訊精簡。
- 「不在服務時段」簡訊即可，例如 `目前非資料收集時段（09:00–17:00）`；**非服務時段不是 API 連線失敗**，切勿自動顯示「企業 API 故障」。避免長段 TLS/認證等內部教學解說。若某項操作因未設定被禁用，簡單說明原因。

### F2. 固定端點狀態（原圖八）

- 表格只保留 **資料來源／目前狀態／最近檢查／訊息** 四欄（窄版可更精簡），不要將 HTTP、responseCode、Schema、最新 sensor data、安全訊息等所有技術欄位平鋪給一般使用者。
- 端點名稱改為 `設備數值（values）`、`設備設定（configs）`、`區域群組（groups）`；括號中的原名為方便開發排查而保留在較次要位置。
- 狀態需依**實際最後一次有證據的檢查**表示：成功、失敗、尚未檢查，服務時段外另作排程提示；不可憑時間段或空白資料推定三支 API 都故障。
- 訊息欄用中文解釋**確知或可能**的原因。401/403 只能寫「可能為網路白名單／權限限制，請確認允許的網路」，**不要直接斷言 IP 錯**；TLS、Timeout、API non-success、schema issue 可以依已知錯誤碼轉中文，不洩漏敏感 Origin/Token/Headers/CA 路徑或完整回應 body。
- 技術細節如仍有診斷需要，只保留在後端 audit／logs 或非預設展開的進階資訊；不因 UI 精簡而破壞原有三層 health 模型。
