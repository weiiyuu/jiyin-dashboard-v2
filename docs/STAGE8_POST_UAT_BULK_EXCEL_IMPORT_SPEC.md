# Stage 8 後｜大量 Excel 一次選取、分批驗證與安全匯入規格

> 狀態：已依現行 Stage 3／5 契約實作，待人工 UAT。
> 預定專案位置：`docs/STAGE8_POST_UAT_BULK_EXCEL_IMPORT_SPEC.md`
> 前置：建議先完成全平台 UAT 文案／介面修正，再單獨進行本功能。本規格是「多檔案操作效率改善」，**不放寬已驗證的單次請求安全上限或既有資料一致性規則**。

## 1. 現況與目標

現行規格可能同時限制：單次最多 **8 份**、單檔 **25 MiB**、單次請求 **50 MiB**，並有解壓體積、儲存格數與解析資源限制。這些數字需先由 Codex 對照現行 API／前端程式核實，不能只以 README 文字為準。

使用者痛點不是單純 50 MiB，而是要反覆打開選檔視窗、每次手動分組 8 份、重複 Preview／Confirm。**期望一次選擇多份檔案，例如 30 份，再讓程式自動切成安全批次依序處理。**

### 成功體驗

1. 使用者一次選取大量 `.xlsx`；畫面保留單一待處理清單與整體檔數、大小。
2. 前端依**實際有效的請求／檔案／解壓限制**自動分組。單次 HTTP 請求仍受原有安全限制，不將 30 份一次發送。
3. 使用者按「檢查全部」後，系統**逐批 Preview**，整合呈現：可新增、完全重複、需確認取代、品質提醒、無法匯入；Preview 不應寫入資料庫。
4. 如有同日不同版本、批內／跨批同來源日期、不可匯入資料，呈現可辨識的處理決策，不偷偷採納後者版本或自動覆寫。
5. 使用者檢視整體結果並確認後，再**依序分批 Confirm**。前一批成功不因後續失敗而被說成「全部回滾」。
6. 顯示全局進度（已檢查／已匯入／重複略過／失敗／待處理），可清楚查看各檔結果與原因，並針對尚未完成／失敗項目安全重試。

## 2. 安全與資料契約（不得退化）

- 沿用既有 Excel 標準化表格驗證、NULL≠0、品質排除規則、日期與 24:00 處理、指紋去重、同日版本替換、Active Batch 單一啟用、Rollback 及 compare-and-swap（CAS）保護。
- 檢查單檔大小、批次請求大小、實際 multipart overhead、展開大小與 cell limits；單檔超標直接在清單中標記，不能偷偷略過造成「總件數不符」。
- 前端分批時，應保守保留 multipart 大小安全餘裕，不能只用 `sum(file.size) <= 50 MiB` 就假設 HTTP 請求一定通過。實際邊界以現行 API 為準。
- 每個 API 仍做**伺服器端**的驗證；前端預檢不是信任來源。
- 不允許並行 Confirm 去競爭同一 SQLite 或 Active Batch；先以循序單一佇列為原則。
- 提前識別同一選取集合中的相同 `source_date`／相同內容重複；按現有指紋與版本語意提示使用者，不以檔案排序決定誰覆蓋誰。
- 所有 Preview 都通過後再 Confirm，**但 Preview 與 Confirm 之間可能存在其他資料庫變動**；Confirm 必須沿用既有指紋及版本 CAS 檢查。一旦版本變更／衝突，停止該部分寫入、提示重新 Preview／確認，不能自動覆蓋。
- 正式匯入的交易原子性應照現有後端實際邊界說明（單檔或單 API transaction）；**多個批次之間不得承諾「全部一起成功或全部回滾」**。
- 重試前必須重新檢查實際資料庫狀態，避免上次已成功但頁面失去回應後重送，導致不必要的替換或重複寫入。
- 不將 Excel 原始 bytes 存到 `localStorage`、隨意持久化到伺服器，或傳往企業 API；本機瀏覽器待處理清單只維持當前工作階段。不承諾刷新頁面／換電腦後可續傳。
- 任何一次匯入仍必須明確標示「Preview 不寫入資料庫」及「需確認替換」；確認按鈕不可隱含自動覆寫。

## 3. 建議 UI 與資料狀態

### 3.1 單一選檔入口

- 「選擇 Excel 檔案」支援多選，畫面顯示 `已選 30 份・共 86 MiB`（僅示意），允許移除單一檔案；清楚區分「選取的全部檔案」與「單次上傳批次」。
- 預設保留原本的原始檔順序，跨批相同來源日期另行提示；可顯示自動分為 N 批，但不要求使用者自行分批。
- 介面可承載大量檔名（內部捲動／分頁），避免 30 份檔案讓頁面無限拉長。

### 3.2 預覽／總覽

- 操作分成明確階段：`已選檔 → 檢查中 → 待確認 → 匯入中 → 完成／部分完成`。
- 批次進度例：`已檢查 18 / 30 份`，旁邊分列 `可新增、重複、需取代、阻擋／失敗、待檢查`；所有狀態計數不得重複加總。
- 品質規則訊息及來源行號採「短標題＋分組詳情」，避免整排文字溢出卡片；沿用第一份 UAT 規格的字數／版面預算。
- 「需替換」應逐檔明確告知日期及受影響 Active Batch，不能無人確認就寫入。

### 3.3 確認與寫入

- 顯示「將新增 X 份、略過 Y 份、替換 Z 份」，讓使用者確認**整體決策**；實際寫入仍循序單批、保留現有 Compare-before-write 安全機制。
- 每一批／每一檔均可辨識狀態：成功、已存在略過、待確認、失敗、未執行。部分失敗後保留已完成結果，剩餘的可以明確重試。
- 重要失敗（同日版本衝突、來源變更、SQLite busy、timeout、413、使用者取消）不得只顯示「上傳失敗」。
- 使用者取消後停止後續批次；已提交成功的批次不可宣稱撤回。

## 4. 技術設計先做輕量盤點

Codex 先找出現有 Preview／Confirm API 的介面、請求限制、transaction 邊界、取消／中止支援與計數語意，再採最小擴充。

優先方案：**前端佇列協調器＋既有安全 API**。不先建立新的後端大檔暫存區、消息佇列或常駐背景服務；若現有 API 無法支援必要的跨批次版本決策，再提出最小後端補強，並說明理由。

需特別核對：
- 多份中的相同日期／相同指紋；新舊版本、跨批替換與 active batch 不一致。
- 預覽期間出現不可匯入／部分品質提醒，是否允許其他檔案繼續檢查。
- Confirm 失敗發生在寫入前、寫入後但回應遺失、SQLite 交易中斷時的各種結果。
- 客戶端記憶體與上傳請求資源、取消後的清理及可見性；不能在前端同時讀取／解壓所有 Excel。
- 批次切分演算法須讓每批皆符合檔數及大小上限，且不可為了提高數量移除後端防護。

## 5. 建議驗收案例（全部用合成 XLSX 與隔離 SQLite）

1. 一次選擇 9、20、30 份，確實自動分批且只需一次檔案選取；`max 8` 與 `max 50 MiB/request` 等實際後端上限仍有效。
2. 文件總大小超過 50 MiB，但每批低於限制，可以分批完成；某單檔超過單檔上限時清楚提示且不影響其他檔案的檢查。
3. 全新、完全重複、同日不同版本、待確認取代、來源品質警告、阻擋錯誤混合，整體摘要及各檔明細一致。
4. 在第 2 批／第 3 批模擬失敗，先前成功已保存且無資料破壞；UI 必須顯示「部分完成」。
5. Preview 後 Active Batch 被其他操作變更，Confirm 拒絕或要求重新確認，沒有靜默覆寫。
6. 重新點擊確認／網路回應遺失後重試，資料庫沒有不預期的重複 Active Batch。
7. 取消、空清單、30 份長檔名、0 筆 Alarm 與來源未提供 Alarm；1280／1366／1440／760px 不水平溢出。
8. 現有少量 Excel（1–8 份）操作沒有退化；Preview zero-write、transaction rollback、NULL/0、Active Batch 歷史及原本人工回復維持正確。

執行聚焦回歸、Typecheck、Lint、Production Build；不要求用私人 Excel 或企業 API 驗證。

## 7. 非目標

- 不直接無條件調高單請求 50 MiB、單檔 25 MiB、解壓／cell 安全限制；不引入跨瀏覽器重開續傳、雲端上傳、外部佇列、大型後端儲存服務。
- 不修改異常事件分析 V2、企業監控、正式 Docker 部署與 SQLite Schema；除非現有 API 契約確實阻擋安全分批，否則不動核心匯入計算。

## 8. 匯入版本紀錄分頁補充

- 沿用既有伺服器分頁 API，不在瀏覽器載入完整版本歷史。
- 上一頁與下一頁之間顯示第一頁、最後一頁及目前頁附近的頁碼；頁數多時以省略號收斂。
- 提供「前往第 N 頁」輸入，可按 Enter 或按鈕跳轉；只接受 `1..totalPages` 的正整數，無效輸入不發出查詢並顯示簡短提示。
- 篩選、排序或每頁筆數改變時回到第一頁；若伺服器因總頁數縮減校正頁碼，畫面同步使用校正後頁碼。
- 僅一頁時不顯示多餘分頁控制；窄版保留上一頁、下一頁及指定頁跳轉能力。
