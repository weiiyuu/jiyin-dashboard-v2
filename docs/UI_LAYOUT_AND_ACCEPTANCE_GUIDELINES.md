# 全專案 UI 版面與驗收規範

> 狀態：Batch A 共用規範
>
> 適用範圍：後續新增或修改的頁面、共用元件、表格與圖表
>
> 經驗來源：Stage 5.1、Stage 5.2 與 Excel 匯入頁最終瀏覽器驗收
>
> 本文件不改變資料契約、統計口徑或既有頁面的核准設計。

## 1. 優先順序與使用方式

發生版面、圖表或互動選擇時，依下列順序裁決：

1. **該頁已核准的最終設計、專屬規格與驗收標準。**
2. **本文件的共用規範。**
3. **UI 框架、瀏覽器與圖表套件的預設行為。**

本文件是共同基線與檢查清單，不是要求所有頁面長得一樣。頁面已有明確的格式、單位、標籤、圖例位置、互動或尺寸時，必須優先照定版設計實作，不得以共用規範為由擅自改動。

若頁面定版設計與資料契約、統計口徑或資料正確性衝突，應先揭露差異、提出最小處理方案並取得決策；不得為了符合畫面而默默修改 API、資料庫、NULL 語意或統計公式。

## 2. 既有設計系統基線

- 優先沿用 `src/app/globals.css` 的既有 CSS token、共用元件與深酒紅暗色視覺語言。
- 優先使用既有 `AppShell`、`PageHeader`、`Panel`、狀態元件、表格與圖表元件；若不適用，先確認差異是頁面需求而非重複建立樣式系統。
- 狀態不可只靠顏色表達；搭配文字、圖示、圖例或可讀標籤。
- 新增共用樣式前先確認現有 token、class 或元件能否完成需求，避免形成平行設計系統。
- UI 規則不授權修改後端資料契約、統計公式、資料品質語意或資料庫 schema。
- 不因導入共用規範而自動重構未列入任務範圍的既有頁面。

## 3. 版面與卡片布局

### 3.1 主要區塊間距由父容器管理

- 同一頁的主要區塊應由父容器以 `gap` 統一管理垂直間距。預設以 **24px** 為參考；若頁面已有核准數值，採頁面數值。
- 主要區塊包含例如篩選區、結果摘要、圖表區、資料表與版本紀錄；區塊內部元件不必一律使用 24px。
- 條件渲染前後應維持相同父容器結構。區塊出現、消失、Loading 完成或資料更新後，剩餘相鄰區塊的間距不能消失。
- 避免以相鄰元素的個別 `margin-top` 拼接頁面節奏。這容易受到 margin collapse、條件渲染、選擇器優先序或元件替換影響。
- 不以相鄰邊框、陰影或相同背景色假裝間距；視覺上與 DOM 量測都應能辨認區塊分隔。

推薦：

```css
.page-sections {
  display: flex;
  flex-direction: column;
  gap: 24px;
}

.page-section,
.page-section > .panel {
  width: 100%;
  margin: 0;
}
```

避免：

```css
.result { margin-top: 24px; }
.history { margin-top: 24px; }
/* result 未渲染或既有 .panel + .panel 規則介入時，節奏容易改變。 */
```

### 3.2 Grid 與卡片高度

- Grid 容器若要自然高度，使用頂部對齊並避免預設 stretch 把短卡拉成與長卡等高。
- 是否等高由資訊關係決定，不以「畫面整齊」為唯一理由強制等高。
- 左右內容高度差距過大時，依序評估：自然高度頂部對齊、重新分區、改為單一全寬布局；不要用大片空白填滿短卡。
- 有大量內容的卡片應設定合理最大高度，搭配內部捲動、分頁或可展開詳情，不能無限制撐高整頁。
- 卡片高度與最小高度應有內容或比較需求的依據，避免造成無意義空白、文字擠壓或操作按鈕遠離內容。

### 3.3 四種常見布局的選擇

| 布局 | 適合情境 | 正例 | 反例 |
|---|---|---|---|
| 等高雙欄 | 兩側資訊地位、內容量與操作節奏相近，且並排比較有意義 | 兩個期間使用相同欄位的比較摘要 | 左側長檔案清單、右側只有三條說明，強制右卡留下大片空白 |
| 自然高度雙欄 | 內容互補但彼此高度不相關，並排仍有助於掃讀 | 篩選表單與簡短查詢說明，頂部對齊 | 使用 stretch 讓簡短說明跟資料表一樣高 |
| 單一全寬卡片 | 同一工作流程、主要操作需要完整寬度，或雙欄高度差過大 | Excel 選檔、限制說明與 Preview 動作整合於同一操作卡 | 將密切相依的操作拆成左右卡，導致規則卡被動拉長或按鈕分散 |
| 分頁清單 | 記錄數可持續增加、需要穩定排序與篩選 | 匯入版本紀錄，顯示總筆數、頁碼及 10/20/50 每頁筆數 | 將所有歷史記錄一次渲染並讓整頁無限增長 |

## 4. 表格與大量資料

### 4.1 資訊層級

- 大量資料先顯示批次或查詢摘要，再提供精簡列表與細節。
- 常用、可比較的欄位放在主列；技術 ID、原始錯誤碼、完整檔名與稽核資訊可放在可展開詳情，但必須可查閱。
- 使用內部捲動、分頁或可展開詳情時，應依資料用途選擇，不把三種模式無差別疊加。
- 避免多層巢狀捲軸。若不可避免，需確保捲動區邊界、焦點與主要操作明確。

### 4.2 表格必要資訊

- 欄名或鄰近說明應清楚揭露單位，例如小時、秒、百分比、日期時區。
- 可排序欄位使用可操作的表頭控制，顯示目前排序欄位與方向，並提供 `aria-sort` 或等價語意。
- 篩選後顯示條件、結果筆數與空結果；空結果不是載入失敗，也不是數值 0。
- 分頁顯示總筆數、目前頁、總頁數、每頁筆數與上一頁／下一頁可用狀態。
- 排序與篩選應作用於完整結果集，再做分頁；不能只排序瀏覽器當前頁。
- 分頁順序需有穩定的最後 tie-breaker，避免翻頁時記錄跳動或重複。

### 4.3 長文字與溢位

- 檔名、規則名稱與長文字容器使用 `min-width: 0`、省略或換行策略；省略時提供完整內容的 tooltip、title 或展開詳情。
- 一般筆電寬度不可造成頁面級水平溢位。寬表格可在明確的 table wrapper 內水平捲動。
- 操作欄不可因檔名過長被推出可視範圍；必要時固定操作欄寬度或調整欄位優先順序。
- 小螢幕不應只縮小字體硬塞所有欄位；可改為卡片列、隱藏次要欄或使用展開詳情，但須遵守頁面專屬設計。

## 5. 圖表設計原則

### 5.1 先確認資料意義

每張圖在實作與驗收前確認：

1. 資料來源、統計口徑、分母與聚合方式。
2. 圖表類型是否適合比較、趨勢、組成或分布。
3. 單位、時間範圍、分桶方式與多序列識別方式。
4. `NULL`、`MISSING_DATA`、`NOT_APPLICABLE` 與有效零值如何區分。
5. 資料增加後標籤、序列、Tooltip 與互動是否仍可讀。

前端只呈現 API 已核准的計算結果，不在圖表元件重新實作 Green、六態、coverage、Alarm 或其它業務公式。

### 5.2 軸線、圖例與互動是檢查清單，不是硬性模板

- 依圖表意義評估必要的軸線、刻度、單位、圖例、資料標籤、Tooltip、焦點與鍵盤互動。
- 趨勢圖通常需要可理解的時間軸、數值單位與多序列圖例；組成條或單值圖未必需要 X/Y 軸。
- Tooltip 不能是唯一資訊來源；觸控、鍵盤或無 hover 環境仍應能理解主要數值或取得可讀摘要。
- 多序列不可只靠接近的顏色區分；搭配名稱、形狀、線型或分面。
- 缺資料不得補 0、跨接或畫成正常線段；有效 0 應保留並能與缺資料區分。
- 資料量大時可減少刻度密度、分桶、分面或提供篩選，但不得改變統計真值。

**本節不要求每張圖都強制具備 X/Y 軸、刻度或 Tooltip。** 若某張圖已有核准的定版形式，以該頁設計及專屬驗收為準。

## 6. 狀態、回饋與可及性

- 正常、Loading、Error、Empty 與大量資料狀態都需有明確呈現；資料更新時避免讓整頁失去上下文。
- Error 文案提供安全、可操作的下一步，不顯示 stack、資料庫路徑、憑證、內部 URL 或未清理的原始 payload。
- Empty 應說明是未選條件、沒有資料、品質不合格或篩選後零結果，不以空白卡片代替。
- Loading 期間停用會造成重複提交的操作，並保留可理解的處理中狀態。
- 操作元件有可見焦點、正確 label 與鍵盤操作；狀態與排序不只靠顏色。
- 資料更新、條件渲染或錯誤恢復後，操作按鈕仍應位於可預期位置。

## 7. 響應式與瀏覽器驗收

### 7.1 基本視窗與條件

- 桌面端優先，同時支援一般筆電解析度。
- 至少以瀏覽器 **100% 縮放**檢查寬度 **1280、1366、1440px**。
- 依頁面風險選擇足以顯示主要內容的高度，並確認垂直捲動與固定區域沒有遮擋操作。
- 每個必要寬度至少檢查：頁面級水平溢位、卡片對齊、文字可讀性、按鈕可達性、表格／清單捲動與焦點。

### 7.2 狀態矩陣

UI 驗收至少涵蓋與任務相關的下列狀態：

| 狀態 | 主要檢查 |
|---|---|
| 正常 | 內容層級、對齊、單位、互動與主要流程 |
| Loading | 不重複提交、不跳動到不可操作布局、狀態可辨識 |
| Error | 安全文案、重試方式、其它區塊不被誤清空 |
| Empty | 原因清楚、不顯示假 0 或假圖表 |
| 大量資料 | 高度上限、捲動、分頁、長文字、效能與操作可達性 |
| 條件切換 | 區塊出現／消失後間距、焦點、排序及篩選狀態保持正確 |

若任務涉及資料語意，還應加入有效零值、NULL／缺資料與部分品質合格等狀態。

### 7.3 DOM 實測與視覺證據

- 任務明確要求間距、尺寸或無溢位時，使用瀏覽器 DOM 實際量測，不以 CSS 原始碼推定結果。
- 相鄰區塊間距可用前一區塊 `getBoundingClientRect().bottom` 與下一區塊 `top` 的差值計算。
- 頁面溢位比較 `document.documentElement.scrollWidth` 與 viewport/client width；表格內部捲動另行記錄，不把預期的表格 wrapper 捲動誤判為頁面失敗。
- 截圖應涵蓋任務指定的關鍵狀態與 viewport，並記錄測試資料性質。私人資料截圖不得提交 Git。
- TypeScript、Lint、單元測試與 Production Build 通過，只能證明程式品質門檻；不能取代真實瀏覽器視覺驗收。
- 若受環境限制無法執行瀏覽器驗收，必須標記「未驗證」及原因，不得以編譯通過宣稱視覺完成。

## 8. 實作與驗收流程

### 8.1 修改前

1. 閱讀頁面專屬設計、驗收文件與相關資料契約。
2. 檢查既有共用元件、CSS token 與同類頁面，確認可重用範圍。
3. 列出要驗證的狀態、viewport、資料量與定量要求。
4. 若頁面定版設計與本規範不同，記錄採用頁面設計的理由，不擅自折衷。

### 8.2 修改中

1. 採最小差異，避免因共用化大規模重構已穩定頁面。
2. 讓父容器負責主要區塊節奏，子元件負責內部布局。
3. 使用合成或公開資料覆蓋長文字、大量資料、缺資料與錯誤狀態。
4. 不為畫面完整而偽造資料、補零或改變 API 契約。

### 8.3 完成前

1. 執行相關 Component／Integration 測試與專案要求的 typecheck、lint、build。
2. 在指定 viewport 以真實瀏覽器操作完整流程。
3. 對間距、溢位、清單高度或其它明確數值做 DOM 量測。
4. 檢查瀏覽器 console、鍵盤焦點、Loading／Error／Empty 與大量資料。
5. 在驗收文件記錄測試環境、資料性質、結果、未驗證項目與必要證據。

## 9. 最小驗收紀錄格式

可依頁面風險調整，但至少記錄：

```text
頁面／功能：
專屬設計依據：
瀏覽器與縮放：
Viewport：1280 / 1366 / 1440
測試資料：公開合成／暫存測試 DB／其它
狀態：正常 / Loading / Error / Empty / 大量資料
DOM 量測：主要間距、頁面 scrollWidth/clientWidth、必要的內部捲動尺寸
互動：排序、篩選、分頁、展開、主要提交／復原流程
結果：通過 / 部分通過 / 未驗證
限制與人工確認事項：
```

## 10. 適用範圍與例外

- 本規範適用未來新增或修改的 UI，不要求立即重構現有所有頁面。
- 已核准的頁面專屬設計可以合理例外，且優先於本規範。
- 純文件或不影響畫面的後端變更，不需製造不相干的視覺驗收工作。
- 新規範應優先強化現有設計系統，不建立另一套 token、卡片或排版系統。
- 若任務只涵蓋單一頁面，不能藉共用規範擴張成全站改版。
- 任何 UI 改動都不得降低資料安全、NULL／缺資料辨識、品質警告或交易一致性要求。
