### C-FUNC-02：選多檔「超過上限」及實際多檔處理

**修正：** 查明現有「每檔 bytes、整批 bytes、檔數、解壓後 bytes、cell count、伺服器 request size」等實際安全上限，在 UI 事前提示可處理份數／總大小，超限時指出是哪種限制（不洩漏內部配置）；保留防 ZIP bomb、安全邊界，不為方便而無條件移除上限。若合理可支援 1、2、4、8 份標準化檔，實作與測試真正多檔 Preview，並依現有契約 **每份獨立 Confirm transaction**；若硬性資源限制不容許單次 8 份，提供明確分批提示或安全分批流程，不能宣稱任意數量皆可。

**驗收：** 以純合成檔測 1／2／4／8 份（邏輯測試可用小尺寸檔，另做代表性的完整 3,840-row 每日工作簿資源測試）、有效／重複／有警告／不合法混合、選檔前移除、Preview 不寫庫、Confirm 逐檔結果與 rollback；對超限原因有清楚中文資訊。不得用企業私人檔案進 Git fixture。

### A-CHART-01：區間模式主圖（P1）

**固定順序：上排左＝逐機台 Green 加工工時趨勢折線；上排右＝各機台累積 Green 工時排行；下排＝六態時間占比。**

**左側折線：**

1. 選 **N 台機器就有 N 組獨立資料序列／圖例**，同一台固定可辨識顏色（機台線色與六態固定燈色的意義須可區分）；不能把全部選台資料加總成單條線。若同值多線重疊，圖例可切換可見性、Tooltip 顯示同一 X 位置各台工時，不假造微小偏差來分離線。
2. 完整 X 軸時間/日期刻度、Y 軸「Green 工時（小時）」刻度（含合理零值基準）、網格、Hover Tooltip、時間／機台／單位；選 30m 或 60m 依 source date 24h 分桶，跨日固定每日桶。所有點都為合法 0 時仍畫有刻度的 0 基準線，不能退化成無刻度點排；缺資料／不適用的點為 null，線段應中斷，不連接或補 0。
3. 同日每個 bucket 的單位是**該 30／60 分鐘內的 Green 小時**；跨日每點是**該日 Green 小時**，不是到當日為止的 running total。計算必須来自後端的 eligible Green 秒之和／3600。
4. 若 API 目前只提供所選機台合計 trend，最小變動加入 `seriesByMachine` 類型的唯讀欄位（實際名稱以現有 contract 為準）、保持舊回應相容，加入 repository／service／route 測試；前端只做渲染。

**右側排行：** 每台機台橫向長條，Y 軸機台、X 軸 Green 小時刻度；按累積時間排序，圖內或末端顯示 `8.42 小時`、`24.00 小時` 等，Tooltip 可讀。合法 0 顯示 0；無 eligible data 顯示「無可用資料」，不可當 0。

**兩主卡版型：** 同一 grid row、頂線與高度一致；不要一張頂端低幾十像素。圖表高度按資料量可讀，避免大量無用途空白；一般筆電可以頁面正常縱向捲動。與下方六態圖保留 20–24px 左右 gap。

### A-CHART-02：六態占比（P1，使用者已確定）

- **區間模式預設「各機台」**：每選一台，就有該台**獨立一根 100% 六態堆疊長條**，顯示機台名稱；可切成「所選機台合計」，此模式使用已核准的「先加有效秒數再除以總有效秒數」，不是平均各機台或各區間百分比。分母為該圖自己的 eligibility，不可套 Green 覆蓋率做分母。
- 保留六態：Green、Yellow、Red、Blue、White、None，顏色一致。中文主標優先（例如「加工中（綠燈）」「黃燈狀態」「紅燈警示狀態」；Blue/White/None 不確定業務意義時保留「藍燈／白燈／無燈號」或來源標籤及說明），**不能把 Yellow 定義為已確認待機、Red 定義為已確認故障**。
- 圖例每個小群組為**色塊＋狀態名稱＋百分比**，字體放大、相鄰排列，避免左邊文字與右邊百分比相距半張卡；必要時換行，但狀態標籤和它的數值不拆散。
- 合計／分機台切換不得改動同一批已查詢來源資料，若逐機台的 share 尚未由 API 提供則最小擴充**唯讀**查詢。0% 明確可辨；NULL/無有效分母為無可用資料，不能假裝六態都 0%；隨台數自然調整高度，去掉目前大片空白。
- **不要把六態占比硬塞進 Green 工時排行**：一張是百分比、一張是小時，問題不同。兩圖相互補充而不混合尺度。

### A-CHART-03：同期比較（P1）

- 依舊契約只在**同期比較**使用 A/B 兩條「全部所選機台合計」折線，避免 8 台×兩期 16 條線；這**不**影響區間分析必須 N 台 N 線。
- 同期比較主圖同樣採**左＝A/B 相對位置趨勢、右＝各機台 A/B Green 工時比較長條**，與區間布局一致。比較排行每台有兩條可辨識的 A/B 長條、數值（小時）與自己期間的 coverage；建議增加 `B−A` 工時差異以便一眼比較，0 基期的百分比變化需標不適用，不能除零。
- 篩選框可叫「期間 A／B」，但**所有結果標題、圖例、Tooltip 必須同時顯示真實日期或日期區間**：例如「A｜2025/06/01」「B｜2025/06/02」，不能只寫「期間 A／B」。
- 日對日：X 軸當日 30m／60m 時刻位置；週對週：第 1–7 日與實際日期範圍；月對月：第 1–31 日位置與各月真實來源日。2 月沒有 30、31 日是 `NOT_APPLICABLE`，不是 `MISSING_DATA` 也不是 0；存在但未匯入的日子是 `MISSING_DATA`。每個期間自己的 coverage 不混在一起。
- **同期六態占比仍依 Stage 2 正式規格：期間 A／B 各一條所選機台合計的 100% 六態堆疊**，各用獨立分母，不直接要求在同比模式新增每機 A/B 八組堆疊，以免擴大範圍。圖例同樣中文化、比例靠近、標示實際日期；下方卡與上方卡有明確 gap。
- 同日 A/B 可合法比較，但可以提示「兩期間相同，結果預期一致」，不是錯誤。

## 4. B｜異常事件分析：語意、清單和表格

### B-TEXT：中文狀態與時間

- 將「Red 狀態時數」顯示「紅燈警示狀態累積時間」；「Yellow 狀態時數」顯示「黃燈狀態累積時間（可能待機）」或相近保守名稱。不要改成「故障次數」或「確定待機次數」。`Alarm` 在 UI 主文案統一「警示」，如「感測器警示紀錄」「警示資料提供情況」。
- 主要時間統計用 `X 小時 Y 分` 或合理的「分鐘／秒」，不要 `0.000 小時`、`11.948 小時`、英文 `2 hours 32 minutes 56 seconds`；若是小於一分鐘的正數不可錯顯 0 時 0 分。詳情保留原始秒數及原文供追溯。聚合來自多台機器時必須顯示「所選 N 台合計」，所以一日可以大於 24 小時。
- 全局移除直接暴露一般使用者的 `Active Batch`、`PROVIDED_NONEMPTY`、`MISSING_DATA`（技術層可留）、`Alarm Sensor IDs`、`查詢 Active 歷史資料` 等混合語句；中文主要名稱要能與來源語意相符，不亂猜單位或機台故障原因。

### B-LIST：連續燈號出現區間（使用者已確定）

- **放棄原本紅黃左右兩大欄**，改為**單一清單＋「全部／紅燈／黃燈」切換**。每列主資訊是燈號、機台、該色**有效秒數的累積時間**；次要資訊是開始與結束時間、涵蓋 3 分鐘區間數、是否跨來源日。資料少時自然高度；多時合理的清單分頁或最大高度滾動，不與空的另一欄同步撐高。
- **不能混淆起迄跨度和實際亮燈秒數**：例如 2025/06/01 00:00 到 2025/06/02 00:00 涵蓋 24 小時，Yellow 累積可能約 11 小時 57 分；主時數顯示後者，次資訊顯示起迄範圍與區間數。0 組時清楚寫「所選期間無紅燈出現區間」，不稱「經證實沒有故障」。
- 不把三分鐘列中的每次黃燈算成多次 fault；原本合併規則與跨日中斷、無效秒數、缺列規則仍以 Stage 2 為準。

### B-ALARM：感測器警示紀錄表與模式切換

- 表格標題固定中文**「感測器警示紀錄」**；主要五欄：「發生時間」「感測器」「警示原因」「事件發生時數值」「持續時間」。原始 sensor ID、ruleValueHigh/Low、raw duration、classification、來源列 ID 等保留在**展開詳情／檢視明細**，別塞同一行。完整時間可 Tooltip/詳情顯示；行內可簡化日期時間但不能使跨日資料失去日期。
- 事件發生時的數值不是即時讀數；來源沒有單位不任意標 `%RH`、`°C`。`durationOriginal` 的英語人類時間可**僅在顯示層**翻為中文時間；缺漏是「未提供」而非 0；原文字串於詳細資訊保留。
- **「顯示內容」三種模式**：①「全部」：狀態相關 KPI/區間及感測器警示都有清楚分區；②「機台燈號」：只顯示適用機台篩選／紅黃結果，不顯示不相關 Alarm 來源；③「感測器警示」：只顯示來源覆蓋、Sensor/Rule 篩選、命中數與警示清單，**不顯示 Red/Yellow KPI 與「無可用資料」的群組**。若「全部」同時顯示兩類條件，說明每個條件作用於哪類資料。
- 來源 `MISSING` =「來源未提供（事件數未知）」；`PROVIDED_EMPTY` =「來源已提供、確認 0 筆」；`PROVIDED_NONEMPTY` =「來源已提供、共 N 筆」。篩選結果 0 筆但來源 N 筆需顯示「**符合條件 0 筆／來源共 N 筆**」，不能誤判 MISSING；0 筆時**不要顯示『第1/1頁』和無作用分頁按鈕**，可給「清除篩選」操作。
- 事件分頁要穩定排序、保留當前篩選條件；長文字不得撐破表格；主行資訊可讀、細節可展開。資料來源 schema 缺欄位時顯示「未提供」，不得虛構。
